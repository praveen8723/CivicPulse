# CivicPulse
## AI That Prioritizes City Problems

Build a complete, responsive web application called **CivicPulse** for the WEBNOVA hackathon.

CivicPulse is an AI-assisted civic issue reporting and management platform. Citizens can report problems such as potholes, garbage accumulation, water leakage, broken streetlights, drainage problems, damaged roads, fallen trees, traffic-signal failures, and similar public infrastructure problems.

The platform analyzes each complaint, determines what kind of issue it is, estimates its severity, checks whether the same problem has already been reported nearby, routes it to the correct civic department, places it on a city map, and tracks the problem until it is resolved.

The product should feel like something a real municipal authority could pilot, not a generic hackathon dashboard.

---

# 1. Main Goal

The core workflow is:

Citizen reports issue  
→ AI analyses complaint  
→ Issue category detected  
→ Severity calculated  
→ Possible duplicate complaints detected  
→ Correct department selected  
→ Complaint registered  
→ Issue appears on city map  
→ Department updates status  
→ Citizen tracks progress  
→ Issue is resolved

The application should demonstrate this entire workflow visually.

---

# 2. Product Roles

There are two primary user experiences.

## Citizen

Citizens should be able to:

- report civic issues
- upload a photo
- describe the problem using text
- optionally record/use voice input
- specify or detect location
- receive an AI-generated issue classification
- receive a complaint tracking ID
- see whether their complaint was merged with an existing issue
- track complaint status
- browse reported problems on the city map
- view resolution progress

## Civic Authority

Authority users should have a dedicated dashboard where they can:

- view all complaints
- see high-priority problems
- filter complaints
- inspect AI classification
- inspect severity score
- see duplicate-report counts
- see issue hotspots
- change complaint status
- assign complaints to departments
- view department workload
- monitor resolution performance

For the hackathon, authentication can be simulated or simplified.

A visible **Citizen View / Authority View** switch is acceptable.

---

# 3. Design Direction

The website should look modern, trustworthy, professional, civic-focused, and premium.

Do NOT make it look like a stereotypical AI website.

Avoid:

- excessive gradients
- glowing neon everywhere
- giant AI robot illustrations
- unnecessary glassmorphism
- random floating elements
- excessive animations
- generic SaaS landing-page sections

Use a design language closer to a modern smart-city command centre.

Suggested visual character:

- clean light interface
- deep navy / charcoal text
- off-white or very light grey backgrounds
- civic blue as primary accent
- green for resolved/safe states
- amber for medium warnings
- orange/red for high and critical issues
- subtle borders
- soft shadows
- rounded but not overly rounded cards
- strong typography
- excellent spacing

The UI should still look impressive enough for a national-level hackathon.

Use meaningful motion only:

- page transitions
- status changes
- map marker interactions
- complaint submission progress
- number counters
- dashboard chart transitions
- small hover interactions

Keep animations fast and subtle.

# 10. Severity Detection

Each issue should have:

- Low
- Medium
- High
- Critical

Also maintain an internal numeric priority score from 0–100.

Do not randomly assign severity.

Calculate it using understandable factors.

Example model:

Base issue risk  
+ public safety impact  
+ affected-area importance  
+ duplicate-report volume  
+ age of unresolved issue  
+ keywords indicating danger

Example:

Traffic signal not working at major intersection:

Base risk = 60  
Traffic/safety keyword = +15  
High-density location = +10  
5 duplicate reports = +8

Priority Score = 93

Severity = Critical

Suggested thresholds:

0–29 → Low  
30–54 → Medium  
55–79 → High  
80–100 → Critical

Show the score where appropriate in the authority interface.

Citizens mostly need the severity label.

# 12. Duplicate Detection

When a new complaint is submitted, attempt to find similar existing reports.

Compare:

- issue category
- geographic distance
- text similarity
- submission time

For the demo implementation, duplicate detection can use:

same category  
AND  
location within approximately 100–250 metres  
AND  
reasonable similarity in complaint description

If a duplicate exists, do NOT create an entirely separate issue case.

Instead create a citizen report linked to the existing master issue.

Example UI:

**Similar Issue Found**

"This problem has already been reported by 6 citizens."

**We've added your report to the existing case.**

Issue:

CP-2026-0892

Show:

7 Citizens Reported This

This feature should be highly visible during the demo.

# 39. Code Quality

This requirement is important.

Write the repository as if it were built and maintained by a competent human developer.

The code should be:

- clear
- readable
- consistent
- modular
- practical
- easy to explain during a hackathon
- appropriately typed
- not over-engineered

Use meaningful names.

Good:

```ts
findNearbyDuplicates()
calculatePriorityScore()
routeIssueToDepartment()
getIssueStatusHistory()
```

Bad:

```ts
processData()
handleThing()
doAIStuff()
executeLogic()
```

Components should have clear responsibilities.

Avoid giant files containing unrelated logic.

At the same time, do NOT create dozens of tiny abstractions for simple one-line operations.

Prefer straightforward code.

---

# 40. Comments Must Feel Natural

Comments should be written only when they help another developer understand:

- why something is implemented a certain way
- a non-obvious edge case
- an unusual decision
- temporary demo behaviour

Do NOT comment obvious code.

Bad:

```ts
// Set status to resolved
issue.status = "resolved";
```

Bad:

```ts
// This function calculates the priority score
function calculatePriorityScore() {}
```

Better:

```ts
// Repeated reports increase priority, but cap the contribution so
// a viral complaint does not automatically become critical.
```

Avoid excessive JSDoc on obvious functions.

Avoid comments such as:

```ts
// AI generated logic
// Generated by Codex
// This code handles...
// This component is responsible for...
```

Do not write robotic tutorial-style comments throughout production code.

Comments should be occasional and useful.

---

# 41. Natural Coding Style

Do not deliberately add mistakes, inconsistent formatting, or poor practices just to appear human-written.

Instead make the code feel naturally authored through:

- consistent naming
- sensible file organisation
- practical abstractions

- reusable logic where reuse actually exists

Avoid adding five layers of abstraction around simple operations.

Avoid generic placeholder names.
